# Pragma HLS：基于文献与代码核对的设计建议

2026-09-10 · 研究建议，尚未实施。完整论证与来源见[英文报告](pragma-hls-design.md)、[阅读笔记](reading-notes.md)和[代码核对](code-ecosystem.md)。

## 最重要的结论

下一阶段最值得研究的是：**让带有状态的数值计算图，通过可组合、可检查的接口，编译成资源有限的空间并行程序；首先以 Cerebras CSL 为后端。**

现有项目已经提供了具体算法、数值参考、受约束的规划器、CSL 生成和历史运行证据。它适合作为下一阶段的基础。真正需要突破的是：加入一个新的算法组合时，能否主要复用已有算子与调度规则，而不用再给整个新图写一套专门的识别、验证、规划和生成路径。

本次整理了 38 篇文献，阅读全文主体的有 8 篇；另核对了 5 个上游项目及 Pragma 的公开代码快照。没有重跑 SDK，没有启动模型实验，也没有把设计建议写入开发工具链。

## 历史背景怎样改变设计

这些研究传统分别回答不同问题，不能全部压缩成“把程序变成一个 graph”：

| 研究传统 | 回答的问题 | 对我们设计的影响 |
|---|---|---|
| 进程网络与早期 dataflow | 并行程序的结果、顺序和状态意味着什么？ | 先定义语义，再谈执行快慢。 |
| SDF、systolic algorithms | 怎样安排生产消费、时空映射与数据复用？ | 同一个算法允许多种合法调度。 |
| 弹性与混合 HLS | 有限缓冲、背压、共享资源如何协同？ | 通信和完成条件必须进入编译器表示。 |
| Halide、Exo、Allo/Dato | 算法、优化与硬件接口怎样复用？ | 算子契约与调度应能独立组合。 |
| MLIR、DaCe、Calyx、AIR | 怎样分层表达状态、控制和物理执行？ | 复用基础设施，但不能省略语义设计。 |
| WaferLLM、MACH | 大规模空间机器有哪些真实约束？ | 处理分布式小内存、控制开销与数据布局转换。 |

对应论文和版本见[主题索引](../README.md#papers)。这张表是研究综合，不表示所有项目沿着同一条历史路线发展。

对熟悉 CUDA 的读者，分块、局部复用、异步传输都不是新概念。不同之处在于，空间编译器需要把更长时间存在的任务映射、分布式内存和通信资源关系表达清楚。GPU 能执行数据流；一张张量依赖图也不会自动成为可运行的物理数据流网络。

## 现有 Pragma 应怎样准确评价

本次核对的是 [MIMD_dataflow 的 dc14c0d 快照](https://github.com/lingzhi227/MIMD_dataflow/tree/dc14c0df54b12cb9e47ae710e2215084154c9570)。

其中，中心验证器会根据算子组合和策略选择专门路径；后续验证器还会检查严格的图拓扑。因此，不能看到“按算子数量分支”就断言它会接受错误图。已核对的 35 节点组合包含残差、共享归一化和完整覆盖等检查，确实有实质工程工作。

问题是这些能力较多依附于特定整图家族。已有内存生命周期检查也有明确边界：它检查声明的计划，并没有声称验证任意 CSL 控制流以及所有 SDK 隐含内存。我们需要把这些声明进一步连接到实际生成代码的完成事件。

公开文档里的 141 个历史受限配置，不能被解释成当前所有组合、所有输入形状都验证通过。该快照中 35 节点候选组合仍待完整 SDK 验证。本次研究没有重新认证这些运行结果。

## 建议的四层设计

1. **算法与状态层**：张量、循环、数值精度、状态更新、终止与 reset，保留独立参考解释器。
2. **空间执行层**：任务、分片、逻辑 channel、collective、流水阶段和依赖；允许选择不同映射。
3. **资源与协议层**：物理缓冲、读写所有权、完成事件、队列、路由、任务和描述符的使用期限。
4. **CSL 后端层**：明确 SDK/硬件版本的能力描述，生成 layout、PE 程序和 host 接口，并输出可追溯的资源报告。

手写 CSL 算子可以继续使用，但必须有契约：数学含义、输入输出布局、数值误差、状态副作用、临时空间、通信顺序、完成事件和已验证范围。契约没有经过实现核对的部分，应列为可信边界，不能直接写成已证明。

## 最容易被忽略的是“什么时候真的完成”

发起传输、发送端不再读取源缓冲、接收完成、下游使用完毕，以及资源上的在途工作全部排空，是不同事件。

例如 `x` 同时进入投影和残差路径，第一条路径结束并不意味着 `x` 已经可以覆盖。只读共享需要等待所有使用者结束。KV cache 的更新还需要明确请求、token 位置和状态版本；迭代求解器同样需要定义迭代间状态。Reset 必须与尚未完成的工作协调。

这些是建议加入的验收案例，不是本次已经发现的现有程序错误。

数值输出正确，也不能单独证明顺序正确、资源无冲突或不存在阻塞。应先选择一个可分析的受限子集，再对明确的有限实例做协议检查。检查器必须说明自己提供的是静态证明、有限模型验证，还是仅观察了一次执行轨迹。

## MLIR 怎么选

建议做渐进试验：用一个小而完整的组合，检验 MLIR/AIR 或 Allo/Dato 的表示能否保留我们需要的状态、通信与资源语义，然后决定集成边界。

不建议先做大规模重写。现有 Python 参考实现和 CSL 验证资产应保留。目录长得像 MLIR，不等于已经采用 MLIR；采用 MLIR，也不等于已经解决死锁、精度或 CSL 后端问题。

上游实现必须按版本比较。当前 AIR、Allo 代码已经有原论文之后的扩展；MACH 的受审阅版本使用 Tungsten/Paint，不能直接当成现成的公共 CSL 后端。这些差异均见[代码核对记录](code-ecosystem.md)。

## 下一步做什么，什么才算完成

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| M0 | 固化已有证据与支持范围 | 每项能力都能追到输入、目标版本、代码和验证状态。 |
| M1 | 建立通用算子与状态契约 | 错误形状、状态使用和精度策略能被明确拒绝。 |
| M2 | 建立通用组合机制 | 新的链式、残差、共享输入组合，不增加专门整图分支也能处理。 |
| M3 | 完善资源与协议检查 | 能发现提前覆盖、顺序错误和有限模型中的阻塞反例。 |
| M4 | 重新认证 CSL 后端 | 指定 SDK 和配置下，生成程序实际运行、数值正确、资源符合声明。 |
| M5 | 验证持续状态应用 | 连续迭代、attention/cache 与 reset 对齐参考；再做小模型整体验证。 |
| M6 | 按研究需要扩展 | 新算法类或第二后端能复用共享语义，差异与限制明确。 |

这是一份后续工作路线，不会自动恢复已经暂停的 SDK 模拟，也不隐含指定新的 Qwen 或其他模型。

选择小组合做 M2 验证，是为了看通用组合是否成立；整个项目的成熟度仍需要复杂例子的回归证据。衡量进步不能只看“又跑通几个例子”，还应看新增组合需要多少专用代码、错误是否更早被检查，以及性能与资源是否仍有竞争力。

## 怎样形成研究贡献

一个可检验的问题是：**包含完成事件和状态所有权的契约，能否让资源受限空间机器上的数值计算组合更通用、更容易检查，同时保留手工调度的有效性？**

需要用同配置手写 CSL、旧生成路径和新组合路径做比较；分开记录精度、设备周期、通信、代码与数据内存，以及编译和模拟的实际耗时。加入消融实验，说明通用契约、内存复用和调度搜索分别带来什么。

要保留失败与拒绝案例。不能把完成一个算子、部分层、一个前缀或一次超时，改写成完整模型通过。只有证据层级清晰，现有 prototype 才能逐步成为有说服力的研究型编译器。
